## 1. 自我检查方法

以"一个人 + 任意技术栈 + 公开可用组件，复刻出同等产品能力"为标准，把复现所需知识分成四层，逐层问"五篇报告覆盖了吗？没覆盖的能在落盘产物里找到吗？":

```
L1 架构与协议（进程拓扑/接口契约/数据模型）     —— 决定"骨架对不对"
L2 核心算法与流程（编辑器/分镜流水线/任务状态机）—— 决定"灵魂在不在"
L3 工程基建（构建/发布/更新/配置/安全/遥测）   —— 决定"能不能长期跑"
L4 生态与内容（技能/知识卡/模型接入/市场）      —— 决定"是不是同一物种"
```

检查动作：对 main bundle / gateway bundle / mcp-tools / 恢复源码做 60+ 关键词地毯式扫描（团队/深链/托盘/代理/崩溃/i18n/二维码/CSP/计费/云协议…），扫描结果见 §7 与下表。

## 3. 八类系统性空白

按复现阻塞度排序。每项给出：**现状证据 → 复现你要做什么 → 补齐成本**。

### 3.1 云协议客户端面（阻塞度：高）

**现状**（本篇新增实证，gateway bundle `../packages/protocol/dist/cloud-gateway.js`）：

```javascript
CLOUD_GATEWAY_URLS = {
  domestic: { dev:"https://hub-pre.xaminim.com", prod:"https://design.minimax.cn" },
  overseas:{ dev:"https://hilo-test.xaminim.com", prod:"https://design.minimax.io" }
};
// 域名迁移期兼容列表（防止 provider baseURL 401）：
LEGACY_PLATFORM_PROVIDER_URLS = ["hilo-pre.xaminim.com","hub.minimaxi.com",
                                 "hub.minimax.io","design.minimaxi.com","platform.minimax.io"];
X-Hilo-Server-Time 响应头  // 服务端时间同步（本地时钟偏差处理）
```

**还知道什么**：JWT（payload 带 `user.deviceID`）、`token:`/`Bearer` 双头兼容、provider 配置经 `/api/v1/apollo/config` 拉取、广告归因 URL 白名单+utm 参数清洗（`normalizeAdAttribution`，MAX_AGE、CLOCK_SKEW_MS、`utm_media_source` 回填）。

**不知道**：服务端如何签发/校验、计费如何按 pricingId 核算、模型代理层如何路由到 H3/veo3 后端、任务如何跨服务追踪。

**复现做法**：自己设计这三样——(a) JWT 签发+refresh（auth:login/renew-token IPC 通道语义可照抄）；(b) pricing 表+estimate 接口（`billing/pricing` 30KB 响应结构可直接抄成自己的定价目录格式）；(c) 云函数/队列化的任务系统（status 机照篇五 §5.3）。

**成本**：客户端协议部分 2-3 天可从落盘源码补齐成文档；服务端要自己设计。

### 3.2 桌面基建清单（阻塞度：高，但全是"体力活"）

自查扫描证实以下子系统**存在于源码但五篇未系统汇总**（main bundle 命中数）：

| 子系统 | 证据（关键词命中） | 复现要做的 |
| --- | --- | --- |
| 深链协议 | `setAsDefaultProtocolClient`×8、`deeplink`×13 | 注册 `minimax-hub-cn://`、DeepLinkOrchestrator（登录回跳/分享打开） |
| 托盘+全局快捷键 | `Tray`×34、`Menu.buildFromTemplate`×5、`globalShortcut`×3 | 托盘菜单+截屏快捷键 |
| 系统代理 | `proxy`×274、`systemProxy`×9、代理 PAC×7000+ | 代理探测/透传给 gateway 与云端调用（`getNetworkProxyMode`） |
| 崩溃收集 | `crashReporter`×2、`minidump`×11 | crashReporter 落盘+上传（自选 Sentry/自建） |
| 登录二维码 | `qrcode`×47、polling×65 | 扫码轮询登录流 |
| 自启动 | `setLoginItemSettings`×6 | 开机自启开关 |
| 多语言 | `zh-CN`×26、i18n 体系 | i18next 双语资源（恢复源码里 i18n 文案全可提取） |
| 多账号/团队 | `invitation`×39、team API 12 路 | 团队邀请/积分转移/成员详情（服务端自己写） |
| 内存治理 | `MEMORY_PRESSURE_RELIEF`、workspace autosuspend | 空闲工作区挂起、内存水位上报 |
| 窗口状态 | windowState 存储 | 几何记忆/最大化恢复 |

**成本**：单项都简单（Electron 文档级），合起来 1-2 周工程量。**关键提醒**：这些散件正是"架构图好看、产品难用"的分水岭，复现时别省。

### 3.3 构建与双轨更新链（阻塞度：中）

**已知**（篇一/三）：Velopack 布局、feed 白名单校验（`velopack/<channel>/builds/<ver>/<stamp>` + SHA-256）、hot-update 仅海外、v3 bundle-manifest 校验。

**不知道**：
- CI 流水线（turbo 任务怎么编排 26 个 workspace 包 + gateway + mcp-tools + opencode 桥 + 技能打包——只存在官方仓库）
- 代码签名证书链与 Windows SmartScreen 处理
- 热更新的**staging→swap 原子替换算法**（关键词 stagingDir/applyHotUpdate 在 bundle 里无命中，实现在 updata-policy-fetcher chunk 中，未精读）

**复现做法**：electron-vite/esbuild 构建 + 你的更新方案（Squirrel.Windows/Tauri updater/electron-updater 三选一即可，Velopack 不是必需）；渲染层热更新可以砍掉（v1 前端 + 全量更新就够 MVP）。

### 3.4 观测与遥测体系（阻塞度：中）

**已知**：meerkat-reporter 埋点域（4 个）、`@cloudcare/browser-rum` 前端 RUM、`/api/telemetry`、诊断上传（`diagnostics.exportLogs/uploadLogs`）、`onLowMemory/onMemoryPressure` 事件、`heartbeat` 路由。

**不知道**：埋点事件的字段 schema（可从恢复源码提，工作量 2-3 天）、RUM 采样策略、指标聚合（prom-client 暴露了哪些 metric——gateway bundle 里可数）。

**复现做法**：事件名+字段自己定义；RUM 换 Sentry/自建 OTLP。**别复刻 meerkat**（那是字节的内部基建）。

### 3.5 聊天/对话前端（阻塞度：中——产品另一半）

877 类里的 ProseMirror/TipTap 族（第四篇只数了类名）、消息队列（`queued_user_inputs`）、`RichUserPromptContent`/`SentAnnotationCards`（第四篇顺带读过）、`textEditSession`/pluginEdit 状态、turn 等待首进度（`turns_waiting_first_progress`）。

**复现做法**：直接用 TipTap 官方栈（React 版）+ 自定义 mention 节点（`asset:` 引用模式照抄：`mentionRef.attrs.path.startsWith("asset:")`）；流式渲染用 streamdown/react-markdown 同款组合。**这块复现成本主要是把 877 类里的聊天族读一遍（约 15 小时）**。

### 3.6 插件系统契约（阻塞度：低——可砍）

3 个捆绑插件 + `hub-plugin-sdk` + `BROWSER_PLUGIN_CHANNELS` 四通道 + `/api/plugins` 运行时。clip-studio 整个前端（index.html/cursor/extensions/fonts）已落盘可直接读。

**复现做法**：MVP 直接砍掉插件系统——它是**架构超前量**（为生态预留），第一版产品不需要。留好 IPC 通道占位即可。

### 3.7 技能与知识内容库（阻塞度：内容问题非技术问题）

18 个 SKILL.md 是**产品内容资产**不是代码——复现技术栈后你面对的是"我的 18 个技能方法论从哪来"。13 张 vendor 知识卡同理（H3 的 prompt 经验是运营沉淀，见篇二 §9）。

**做法**：技能文件格式（frontmatter: name/description/trigger-words + 正文 + references/）已经完全清楚，可以先写 2-3 个简单技能（如"口播视频"）验证流程，方法论随运营积累。

### 3.8 工程细节的长尾

- ffmpeg/ffprobe 装配（`resolveFFmpegPath`，resources/ffmpeg/ 已见）与媒体管线（concat/lip-sync/ASR 的本地 vs 云调用分布）
- opencode 桥接协议（:4096 MCP，第三篇提取了 RPC 面）
- `AgentProfileRegistry` 多版本档案的安装/切换实现
- Windows junction 安装目录管理（`windows-junction-path` chunk）
- 技能市场白名单/签名校验（`market/whitelist`）

这些都能从落盘产物补齐，合计算 3-5 天阅读。

## 4. 无法从客户端补齐的：云端服务端

必须直说：**这个产品的一半以上在云端，源码不在你机器上**。客户端能观察到的只有：

| 云端子系统 | 客户端可见面 | 你要自建什么 |
| --- | --- | --- |
| 账号/鉴权 | JWT 格式、login/refresh 通道语义 | 用户系统 + token 服务 |
| 模型聚合网关 | capability 目录结构、pricing 响应结构、task problem.upstream 诊断格式 | **对接 H3/veo3/kling 的代理层**（各家有自己的 API，公开可签） |
| 任务调度 | status 机、progress phase、outbox 投递语义 | 队列 + 状态机 + 轮询/推送 |
| 计费/积分 | estimatedCredits、wallet、concurrency limits | 定价表 + 扣费/退款 |
| 技能市场 | market API 面（search/install/whitelist/operator…） | 技能 CDN + 审核 |
| 团队协作 | invitation/credit transfer/member API 面 | 组织/权限模型 |
| 内容安全 | （不可见——上传与生成的审核必然在服务端） | 自建或买（复现出海版必须处理） |

**好消息**：这些服务端的**客户端契约**（API 形状、状态语义、错误结构）在五篇里已经逆向得很全——等于你拿到了一份**服务端 API 需求规格书**。按契约自建服务端，是复现里最常规的部分。

## 5. 技术栈替换建议表

原栈逐项给替代（按"换掉省多少事"排序）：

| 原组件 | 复现选型 A（贴近原栈） | 选型 B（更省） | 备注 |
| --- | --- | --- | --- |
| Electron + React 19 | 同 | **Tauri 2 + React**（体积/内存/安全都赢） | 但内嵌浏览器+多窗口编排 Tauri 也能做；若复刻"AI 剪辑"插件宿主，Electron 生态省事 |
| NestJS gateway（20MB 单 bundle） | **Fastify + zod**（结构同款） | Hono/Node http | 关键不是框架是**契约**：357 路路由表、zod 校验（原文用 zod 风格 schema）照抄 |
| opencode（agent 宿主） | **直接用开源 opencode** | 自己薄封装 MCP SDK | 它本来就开源——**自研 agent 提示词 + 工具面**才是你该写的（篇二 §5 的提示词是最高价值蓝本） |
| mcp-tools（MCP server） | @modelcontextprotocol/sdk 官方 TypeScript SDK | 同 | 5 个动词（execute/deliver/task_query/wait/resolve）+ zod schema 照抄 |
| SQLite（better-sqlite3） | **SQLite + Drizzle/Kysely** | Postgres（多用户时） | 篇二/三的三层指纹资产表直接抄——这是最好的资产建模范本 |
| Vite + 26 workspace 包 | **Turborepo + Vite** | Nx | 包边界本身就是架构文档，照切 |
| Velopack 更新 | electron-updater / Tauri updater | — | feed 白名单校验逻辑值得抄（篇三 §5） |
| TipTap 聊天流 | TipTap 官方 | 同 | mention→asset: 引用设计照抄 |
| 画布编辑器 | **直接抄恢复源码**（3000 行可读） | — | 篇四是现成实现文档 |
| RUM/meerkat | Sentry | OpenTelemetry | 事件 schema 自定 |
| 技能文件 | markdown + frontmatter 格式照抄 | 同 | — |

**唯一不可替换项**：模型（H3/veo3/kling…）只能是 API 客户户；vendor 知识卡要按你实际接的模型重写。

## 6. 复现优先级路线图

按"最早见到能用的东西"排序：

```
P0 决策（1天）    选栈（§5）、砍范围（无插件/无热更/无团队=砍40%工作量）、定 LLM 接入清单
P1 骨架（1-2周）  桌面壳 + 本地 gateway + SQLite 对象模型（照 19 版 SQL）
                 + execute/deliver/task 五动词（先只接 1 个模型，如 H3 API）
P2 灵魂（2-3周）  agent 提示词（抄篇二§5 结构）+ 能力协议 + 计费确认闸门
                 + 确认卡（question）通道 + 画布编辑器（抄篇四）
P3 流水线（2周）  分镜文档（storyboard_review.md 模式）+ revision/Approval 状态机
                 + Preflight 校验器（抄 mcp-tools 校验器结构）+ 技能×2 自写
P4 基建（2周）    更新通道 + CSP/沙箱 + 观测 + 桌面长尾（§3.2 清单）
P5 生态（后置）   插件通道占位、技能市场 API、团队
```

**总估算**：1 人全职 8-12 周到"单机可用、接 1 家模型、跑通剧本→分镜→视频"的 MVP；团队功能/市场/多模型另计。

**最重要的复现心法**（五篇分析的总结论）：这个项目的竞争壁垒不在任何单一技术，在于**把不可靠生成关进可靠流程**的四件套——对象模型（Resource/Version/Composition）、门禁（确认卡+revision）、合同（capability schema+Prompt 锁定）、血缘（ID 链）。技术栈全换掉，这四件套的**语义**必须原样带走。

## 7. 本次自查新增的三个实证补丁

自查不是空谈，顺手补了三个此前文档没有的实证：

1. **云网关 URL 矩阵 + 域名迁移兼容表**（§3.1 已引原文）：`cloud-gateway.js` 的 CLOUD_GATEWAY_URLS 四区×四通道 + LEGACY_PLATFORM_PROVIDER_URLS 五个旧域名白名单——**"token 注入按白名单域名过滤，否则 401"**是复现多环境客户端必须抄的细节。
2. **双 CSP 实证**：v3 工作台 `default-src 'none'; script-src 'self'; …connect-src ws://127.0.0.1:* …`（每窗一份硬 CSP）；主窗口 CSP 由 gateway URL 动态拼装（`connect-src` 注入 gateway/CDN/RUM/track 端点，dev 才有 react-scan）——**CSP 是"app 级 gateway URL 不允许端口漂移"（allowPortDrift:false）注释的原因**：CSP 烘进窗口创建参数后改端口=全废。
3. **GatewayManager 装配契约**（main bundle 原文）：gateway 子进程的全部注入参数（region/channel/proxy 模式/auth snapshot/API base/update base/hot-update base/track/rum/lane/configDir/entryPath/**preferredPort+allowPortDrift**/runtimeEnv/agentProfile{knowledge,contracts,workflows}/opencodeDbPath/onRuntimeEvent）——**这份参数表就是"桌面壳如何孵化 gateway"的完整 API**，复现时照单全收。
