## 1. 桌面基建长尾

10 项子系统全部读完（main bundle `index-WiZKxTAT.js`）：

### 1.1 深链协议（DeepLinkOrchestrator 类，全文 60 行）

```
handleUrl(url):
  parseDeepLink(url) → 失败丢弃
  isDuplicate(rawUrl) → recentlyHandled Map + DEDUPE_WINDOW_MS 去重窗口（防双击/系统重放）
  取窗口：windowService.getHomeWindow() ?? getMainWindow()
  有窗：restore→show→focus → sendActionToRenderer（IPC DEEPLINK_RECEIVED）
  无窗：enqueuePendingAction（上限 MAX_PENDING_ACTIONS，FIFO 溢出丢弃），窗口创建后 flushPendingToRenderer
  同时 handlers.get(action)?.(parsed) —— 主进程侧处理器注册表
```

**要点**：渲染层与主进程双通道接收（渲染层走 IPC 通道，主进程按 action 注册 handler）；日志脱敏 `redactDeepLinkForLog`（深链可能带 token）。协议注册 `setAsDefaultProtocolClient`（8 处，含 dev 模式路径解析 `resolveDevProtocolAppPath`）。

### 1.2 代理系统（NetworkDiagnosticsMainService）

- **两种模式**（实证）：`"direct"`（`session.setProxy({mode:"direct"})`）和 `"system"`——**没有 PAC/固定服务器自定义配置**，就这两档
- `setProxyMode` 走**串行更新队列**（`proxyModeUpdateQueue` 链式 Promise），防并发竞态
- **失败回滚三件套**（原文）：Chromium 代理回滚 + 配置回滚 + 环境变量回滚（`HILO_NETWORK_PROXY_MODE`），回滚失败收集为 rollbackErrors 上报
- 诊断快照 `lastSnapshot` 只读复用（"observe-only, no fresh network IO"）
- **代理模式如何传给子进程**：GatewayManager 装配参数里有 `getNetworkProxyMode`——gateway 启动时取当前模式透传

### 1.3 登录流（startLogin + loginWindow，47 处 qrcode 引用）

实测逻辑（原文结构）：
- **平台分支**：macOS dev 模式可用系统浏览器（`devAuthBrowser === "system"` 偏好）；Windows 走**协议回跳深链**（`supportsInAppFallback() === win32`，依赖深链协议注册成功）
- `loginWindowAttemptId`（UUID）+ `dispatchSeq`（递增序号）双标识——**登录尝试幂等**（旧窗口回调被 attemptId 不匹配丢弃）
- 登录窗口是独立 BrowserWindow，加载云端 `loginUrl`（篇一实测 `design.minimax.cn/login`），成功后页面跳深链 `minimax-hub-cn://` → DeepLinkOrchestrator 接住 → auth token 入库
- **qrcode 47 处引用主要在渲染层**（登录页 UI 渲染扫码二维码 + 轮询状态）

### 1.4 自启动与系统集成（ConfigService 驱动）

```javascript
const runOnStartup = config.runOnStartup === true;
this.setLoginItemSettings(runOnStartup);
if (!runOnStartup) this.cleanupLoginItemsInBackground();  // ← 清理历史残留的登录项（Windows 注册表遍历）
if (config.preventSleep) this.startPowerSaveBlocker();    // powerSaveBlocker 防休眠
this.registerGlobalShortcuts();                          // globalShortcut（截屏快捷键）
app.on("browser-window-focus", ...)                      // 焦点变化重挂快捷键
```

**要点**：`cleanupLoginItemsInBackground` 专门处理卸载残留/多版本冲突的启动项——Windows 自启动的脏状态治理，复现时容易漏。

### 1.5 托盘

`Menu.buildFromTemplate`：菜单首项"新建项目"（`MENU_NEW_CHAT` IPC），无窗时 `showHomeWindow()`。托盘随 `menuBarVisible` 配置创建。**托盘是极简的**（无复杂菜单树）——产品重心在主窗口。

### 1.6 多语言

`resolveLocale()`（12 处）+ `toHiloLang()` + `rebuildNativeMenus(config.language)`（配置切语言时**原生菜单重建**）+ gateway 侧 `userLang` 装配参数。渲染层 i18next 双语资源已在恢复源码中全可见（第二篇技能列表实测双语字段）。

### 1.7-1.10 其余四项

- **内存治理**：`MEMORY_PRESSURE_RELIEF` IPC + `app_memory_warning` 埋点 + 渲染层 `onLowMemory/onMemoryPressure` 桥成员（篇一）+ 工作区 autosuspend（环境变量组）——三层联动
- **崩溃收集**：`crashReporter`（2 处启用）+ minidump（11 处处理）——落 userData，随 `log:upload` 上报
- **多窗口**：windowService（getFirstWindow/getHomeWindow/showHomeWindow）+ windowState 存储（`maxOpenProjects` 限制）
- **窗口几何**：`windowState` 存储键（第一篇存储节点清单）持久化

## 2. 构建发布链

新增精读：`update-policy-fetcher-CYQPhXS_.js` chunk 全文（12.9 KB）——**更新策略（要不要更新）独立于更新器（怎么更新）**：

### 2.1 更新策略协议（云控灰度）

```javascript
UPDATE_POLICY_TIMEOUT_MS = 3000          // 策略拉取超时 3s（不阻塞启动）
UPDATE_POLICY_CACHE_FILE = "update-policy-cache.json"
CACHE_TTL_MS = 24h                       // 缓存一天
UPDATE_POLICY_FETCH_MAX_ATTEMPTS = 3     // 重试 3 次
RETRY: 250ms 基数 ×2^n，上限 1000ms      // 指数退避
HTTP_SERVER_ERROR_MIN_STATUS = 500       // 5xx 才重试
```

**策略内容**（parseCdnPolicy）：
- `manual_download_url`——强制手动下载的跳转链接（协议白名单校验，invalid 只 warn 丢弃）
- `manual_only`——**按平台+版本区间禁用自动更新**（`platforms[]` + `min_version_inclusive`/`max_version_exclusive` + 中英双语 reason）——**这就是"某版本出事故时云端一键停更"的机制**
- `updated_at` 时间戳

**缓存设计**：`{policy, cachedAt, metadata:{region,channel,platform}}`——**元数据不匹配（换区/换通道/换平台）即弃缓存**；过期不删除（"retaining as LKG fallback"——**过期策略作为最后已知好策略继续兜底**）。

### 2.2 安装目录重定位（RELOCATE_MARKER）

托盘读取时顺带发现的：`minimax-hub-relocate-result.json` 标记文件（schemaVersion 1，4KB 上限，BOM/UTF-16 解码兼容）+ 五种结果枚举 `success | uninstall_failed | install_failed_rolled_back | install_failed_old_restored | install_failed_fatal`——**应用搬家（换安装目录）是带事务回滚的自定义流程**，标记文件让启动时能检测上次搬家结果。GIB 常量（磁盘空间检查）也在场。

### 2.3 CI/签名（仍不可补）

诚实声明：CI 流水线与代码签名只存在官方仓库，客户端源码只见其产物（sq.version、nupkg、junction 结构）。复现用 electron-builder/Tauri 的标准签名链即可。

## 3. 聊天前端

关键实证：**聊天流不在渲染层直接连云端，走 gateway 的 opencode 桥**：

### 3.1 sendMessage 桥接协议（gateway bundle 原文注释）

```javascript
/** ...The opencode side streams back via SSE so we do NOT need the HTTP
  * response. We race the fetch against a short timer: if no error arrives
  * within 10 s, we assume the request was accepted and return. */
async sendMessage(sessionId, text, model, system, _directory, fileAttachments,
                  sourceType, onBackgroundFailure, languageDetectionText,
                  attachmentRefs, projectContext, beforeSubmit, fileMentionDisplayNames)
```

- **提交**：POST 到 opencode（:4096），10 秒**宽限窗口**（`grace_window`）——HTTP 响应放弃等待，事件全走 SSE
- **后台失败**：`onBackgroundFailure` 回调 + 详细日志（`accepted_by=grace_window elapsed_after_accept_ms=`）
- **流式**：SSE（渲染层 18 处 SSE 引用 + v3 preload 24 处）——`ChatMessageEnvelope` 每步一帧（见 §5.3 插件同款协议）
- **文本摘要旁路**：gateway 自己也直连云端 `/api/v1/messages`（`text-version/summarize` 标签，`SUMMARY_MODEL` + `thinking:{type:"disabled"}` + max_tokens）——**文档版本摘要不走 agent**，独立 LLM 调用

### 3.2 渲染层结构（p4/p5 命中）

`useChat`（38 处使用）、`ChatPanel`（props 含 `annotations/activeAnnotationId/textEditMode/pluginEditSession/v3TextEditSession`——**聊天面板是多编辑上下文的宿主**：文本编辑会话、插件编辑会话、标注列表全部挂它上面）、`queuedMessage`（离线/忙时排队）、`AssistantMessage/UserMessage`、`turns_waiting_first_progress`（首进度等待指标）。

**复现配方**：opencode SSE → gateway 事件流 → 渲染层 TipTap 文档（`mentionRef` 节点 attrs.path = `asset:<id>`）+ 消息队列 + 流式 patch。篇四的 `RichUserPromptContent/SentAnnotationCards` 已覆盖展示层。

## 5. 插件系统

### 5.1 hub-plugin-sdk（gateway/node_modules/@hilo/hub-plugin-sdk，15 文件，.d.ts 完整可读）

**这是本篇最大的收获**——插件系统的完整契约以 TypeScript 声明形式躺在 gateway 的依赖里：

**协议层**（protocol.d.ts）：
```
HUB_PROTOCOL_VERSION = '2'
RpcRequest  { kind:'hub:rpc:request',  v, id, method:点路径如 'canvas.getIncomingResources', args }
RpcResponse { kind:'hub:rpc:response', v, id, ok:true,result | ok:false,error }   ← id 匹配
HubEvent    { kind:'hub:event', v, topic, payload }
  topics: incoming | storage | config | billing:changed | app:changed
        | main:registered | main:unregistered | main:invoke
        | chat:message | chat:done | dag:done(按 runRegistry 定向)
```

**关键注释原文**（复现必读）：
- "Mirrors Figma's `figma` object in shape but not scope"——**插件模型对标 Figma**
- **大负载提升**："large binary payloads (Blob/File) MUST be lifted out before send (the SDK uploads them to the gateway first and substitutes a BlobRef)"——RPC 只传引用
- **app:changed 增量**："the host only sends the fields that actually changed, the SDK merges"——差量事件
- **chat 帧广播+SDK 过滤**："Host fans out unconditionally (every iframe receives every frame); SDK filters by sessionId"——宿主无状态，过滤在 SDK
- **DAG 定向**："the host knows ownership at submit time (every hub.dag.submit registers run ids against the calling iframe)"——与 chat 相反，DAG 按归属推送

**API 面**（api.d.ts，HubApi 接口）：
`version / ready / canvas / storage / config / billing / comfyui / ui / log / app / chat / skill / dag / files / python / agent / locale / theme / region / gpuAccelerationDisabled`

**配套类型**（types.d.ts 导入表）：AddPlaceholder(Group)Args、ChatSendArgs、DagSubmitArgs、PickAssetOptions、PythonRunArgs、SuperResolutionArgs、UploadToCdnArgs、WriteToPluginDirArgs……——**插件能做的一切**：画布占位、聊天、DAG、选资产、跑 Python、超分、传 CDN、读写插件目录。

### 5.2 宿主侧（browser 插件通道 + 装载模型）

```
BROWSER_PLUGIN_CHANNELS = {
  GET_CONFIG: "browser-plugin:get-config",   // tab preload→main (invoke)：本 tab 运行配置
  EVENT:      "browser-plugin:event",        // tab preload→main (invoke)：插件事件，ack 回执
  COMMAND:    "browser-plugin:command",      // main→tab preload (send)：运行时命令
  RENDERER_EVENT: "browser-plugin:renderer-event"  // main→宿主渲染层：已校验解析的事件
}
BROWSER_PLUGIN_IDS = ["image-hover"]         // 浏览器侧插件目前只有图片悬停一个
BROWSER_PLUGIN_IMAGE_ACTIONS = ["chat","canvas","clipboard","edit"]
BROWSER_IMAGE_EDIT_ACTIONS = ["remove-background","upscale","describe-prompt","separate-layers"]
```

**画布插件的宿主**：clip-studio/导演台/comfyui 是 **iframe 形态**（SDK 注释通篇 iframe↔host），不是 WebContentsView——RPC 走 postMessage，Blob 预上传换 BlobRef。

### 7.2 Windows junction 管理（windows-junction-path chunk，全文精读）

```
APP_JUNCTION_ROOT_NAME = "MiniMaxHub"
junctions 根候选: %ProgramData%\MiniMaxHub 或 %PUBLIC%\MiniMaxHub
junction 名 = windowsJunctionHash(targetDir) 前 12 位 hex（模式 ^[a-f0-9]{12}$）
解析链: stripWindowsNtPathPrefix(\\?\) → normalize → readlink → 校验目标绝对路径
       → 重建期望 junction 路径并比对（**目标哈希必须与 junction 名一致**，防篡改指向）
返回 {kind:"not-managed"|"invalid"|"resolved", installDir, reason}
```

**用途**（与篇一 velopack 壳联动）：安装目录经 junction 指向真实位置，更新时**切 junction 而非移动目录**——`VELOPACK_JUNCTION_INVALID` 时拒绝更新（篇一 §5）。

### 7.3 技能市场白名单（main bundle）

启动时并行拉 `/api/skills` + `/api/skills/market/whitelist`（3s 超时）；`unloaded = whitelist.filter(名字未加载 && 磁盘不存在于 installedSkillsDir 与 subAgentSkillsDir)` → 触发安装。**白名单是"云端指定必装技能清单"**——18 个捆绑技能由此下发，主进程负责对账安装。
