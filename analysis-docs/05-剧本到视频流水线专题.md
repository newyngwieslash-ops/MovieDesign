## 1. 全景图

```
用户一句话（"做个 15 秒片头"）
   │
   ▼
┌─ 第1层 Skill（~/.hub/skills/*/SKILL.md）────────────────┐
│  导演方法论：Intake→画风门禁→色彩合同→分镜→Prompt合同    │
│  产出：受门禁保护的"创作状态机"                          │
└──────────────┬──────────────────────────────────────────┘
               ▼  media-agent（opencode，第二篇§5 提示词）
┌─ 第2层 语义分镜（文档层）──────────────────────────────┐
│  Panel → Logical Shot → Master Timeline                │
│  storyboard_review.md（画布文档节点，带 revision）      │
└──────────────┬─────────────────────────────────────────┘
               ▼  用户批准（确认卡）
┌─ 第3层 Prompt 编译 + Preflight ─────────────────────────┐
│  final_video_prompt.md（字符级锁定，5000-7000 字）      │
│  生成锁全过 → 派单                                     │
└──────────────┬─────────────────────────────────────────┘
               ▼  design_execute
┌─ 第4层 Gateway 执行（:8001）───────────────────────────┐
│  capability 解析 → 计费确认（waiting_user/billing）    │
│  → 后端调用（H3/veo3/kling…）→ task 状态机            │
└──────────────┬─────────────────────────────────────────┘
               ▼  design_deliver / task 产出
┌─ 第5层 对象模型（SQLite，第二篇§3）────────────────────┐
│  outputs → Resource + Version → Composition 放置      │
│  画布节点 = 创作对象呈现（v3 canvas 协议）             │
└────────────────────────────────────────────────────────┘
```

**核心认知**：这条流水线上**没有一处是"AI 自由发挥"**。每一层都是"机器执行 + 人类门禁"的交替——AI 写分镜，人批准；AI 编译 Prompt，机器 Preflight；机器扣费前，人确认。整个体系的设计目标就是把"不可靠的生成"关进"可靠的流程"里。

## 2. 第一层：Skill = 导演方法论

Skill 不是"提示词模板"，是**成文的制作流程合同**。以最完整的 `anime-game-pv`（257 行）为例，它定义了：

### 2.1 生产实体表（SKILL.md 原文摘录）

| 实体 | 定义（原文） |
| --- | --- |
| `Candidate Ref Capsule` | 媒体分析产生的候选素材贡献；只描述可能角色，**不具有最终画风或执行权限** |
| `Style Authority` | 真正进入视频 Prompt 的**唯一**画风权威；类型只允许 `existing_asset` 或 `generated_asset` |
| `Palette Authority` | 最终进入视觉权威图与视频 Prompt 的**色彩合同**（黑白结构 + 一个高纯度主题色 + 可选极少量强调色） |
| `Panel` | 语义分镜中某个时间点或状态的**制作单元**（构图、动作进度、连续性） |
| `Logical Shot` | Master Timeline 内一段连续叙事，包含一个或多个 Panel；**它是提示词章节，不是独立视频资产** |
| `Master Timeline` | 包含全部 Logical Shot 的**唯一**完整生成计划 |
| `Storyboard Package` | 一次可供用户审阅的完整分镜版本（storyboard_review.md + Panel + Shot + Timeline + 可选九宫格） |
| `Storyboard Approval` | 用户通过真实确认卡给出的批准回执；**必须绑定 `storyboard_revision`** |
| `Render Contract` | 一次完整生成的可执行合同；draft 锁能力与计划，locked 锁身份/画风/色彩/槽位/参数/预算 |
| `Render Attempt` | 一份已确认合同 + 一份过 Preflight 的 Prompt + **一次完整视频生成** |

### 2.2 生产拓扑（原文固定顺序）

```
静默 Intake → 制作路线与身份确认 → Style Authority Gate → 色彩方向与参考处理
→ 视觉权威决策 → Render Contract draft → 必要视觉权威图与唯一 style_authority
→ locked Render Contract → Panel → Logical Shot → Master Timeline
→ 可选九宫格 → 完整 Storyboard Package 确认
→ final_video_prompt 编译与 Preflight → 生成一个完整 Render Attempt
```

**硬约束（原文）**："每个 Render Attempt 始终生成一条完整候选视频；多个独立最终成片、时长超过 15 秒或跨视频连续性均超出本 Skill 的交付范围。"

**为什么是 15 秒**：模型单次生成的可靠区间（第二篇实测模型目录：H3 时长选项 4-15 秒）。Skill 的范围声明本质上是**把产品边界钉在模型能力的可靠区**。

### 2.3 色彩预算（内部默认视觉路径的量化规则）

原文規則——主题色"保持同一色相家族，可改变明度但不能漂移为邻近彩虹色"；强调色"**单帧不超过 5%、全片平均不超过 3%**，不能成为背景、整套服装、大型道具、城市灯光系统或持续轮廓光，并应长时间消失后再在唯一语义节点出现"。

这是**把视觉设计规范写成了可校验的数值约束**——AI 执行时可对照检查，质检时可判定。

## 3. 第二层：剧本与分镜的语义体系

### 3.1 剧本怎么来

两条路（第二篇 + 本篇证据）：

**路 A（画布快捷指令）**：画布 QUICK_PROMPTS 的第一个就是"剧本生成"（p2 恢复源码）：

```text
promptFallback: "请创作一个[时长]的[类型]剧本。\n主题：[一句话描述]\n情绪基调：[温暖/悬疑/搞笑/热血]\n特殊要求：[如有]"
```

→ 走 `design_execute` 的 `generate_text` 能力 → 产出剧本**文档节点**（画布上的一页 markdown）。

**路 B（mcp-tools 的 plan 体系）**：`mcp-tools/dist/main.js`（2.4MB bundle）里有一套**分阶段计划（Plan）+ 工作项（work item）校验器**，用于更长的剧集类内容：

- `workflow_kind` 枚举（detectWorkflowKind 原文）：`drama-series`（剧）、`mv`、`ad-tvc`、`general-video`、`koc-video`、`trailer-video`、`generic`
- Plan 的 stage 状态机：`["waiting_user", "doing", "done", "blocked"]`，等待原因 `["plan_review", "result_review"]`
- 每个 stage 有 `stage_fields`（如 `max_generated_clip_duration_s`）和 `execution_locks`（如 `aspect_ratio`——**画幅在阶段级锁一次，所有工作项继承**）

### 3.2 剧本 → 场景 → 分镜格 → 视频项（drama-series 校验器，逐行核实）

mcp-tools 里的校验器体系**就是剧本的机器可读 schema**。drama-series 工作流要求每个视频工作项必须携带（validateDramaVideoItem 原文要求）：

```
clip_group_id（镜头组）+ sequence_index（组内序号）+ duration_target_s（目标时长）
scene_id / source_scene_beat_range / source_scene_range（来源场景或节拍区间——三选一）
refs（角色参考 id 绑定）+ audio_approach（声音方案）+ prompt（作者化的就绪提示词）
aspect_ratio（画幅） + blocking 信息（roles_present 在场角色 + persistent_background_roles 背景角色）
```

配套校验规则（全部原文）：

- **ref 覆盖检查**（validateDramaBlockingRefCoverage）："refs must include enough role reference ids to cover blocking.roles_present and blocking.persistent_background_roles"——**每个在场角色都要有参考图**，否则报错
- **背景角色与在场角色必须不相交**（validateDramaBackgroundRoles）
- **时长上限**（validateVideoDurationCap）："duration upper bound ${durationCap}s exceeds max_generated_clip_duration_s ${cap}s"（默认 15 秒）
- **ref 只能是稳定 id**（validateDramaSourceRefIds）："refs must contain stable ref ids only; write role labels in prompt/blocking fields"——**ref 槽位与叙事文字严格分离**

### 3.3 分镜格（scene-keyframes）

`validateDramaSceneKeyframeItem` 是"剧本→分镜"这步的机器合同（原文）：

```
storyboard_style = "bw_blockout" ? 8 格 : 9 格      ← 黑白草稿版 8 格，标准版 9 格
prompt 必须自包含：第1格…第9格 的内联分格块（cell_1..cell_N）
禁止单独的 cells 字段（"drop the cells field and write the panels inside the prompt"）
每格必须存在（hasPanelMarker 逐格检查："prompt must inline 第N格"）
"prompt must inline 第${index}格 — write ${panelCount} ordered Chinese panel sections"
```

**这是"九宫格分镜"的协议层**：分镜不是结构化数据（每格一个字段），而是**约定的中文分格文本语法**（"第1格：…"），靠校验器逐格检查存在性。与技能层的"可选九宫格预览"（用图像模型把分镜渲成 3×3 图）互为表里：**语义分镜是文本权威，九宫格只是可视化预览**。

## 4. 第三层：门禁与确认

### 4.1 确认卡（Question Window）是唯一的同意形式

anime-game-pv 原文（ Interaction Contract 节）：

> "任何需要用户选择、确认或批准生成的步骤都必须调用真实 确认卡。普通文本只能解释结论、说明影响或请求上传已选素材；**不得在普通回复中列编号选项、用'请回复 1/2/3''如无修改我就继续'代替**"

**技术实现**（第二、三篇已覆盖）：gateway 的 `/api/question/request` 路由 + media-agent 提示词里 `question` 工具 permission=allow——**同意必须走结构化 UI 通道**，聊天文本里的"好的/可以"不算数。这是对 LLM"把用户客气话当授权"倾向的工程防御。

### 4.2 失效传播链（原文，方向性设计）

```
style_source / visual_policy 变化 → 配色、参考处理、视觉权威、Render Contract、
                                   Storyboard Approval 全部失效 → prompt_status=pending
配色 / 强调色职责 / reference_processing 变化 → 视觉权威 revision 失效
                                   → Render Contract + Approval 失效
Panel / Logical Shot / Master Timeline 变化 → 新 storyboard_revision → Approval 失效
只改模型 / 合法参数 / 参考槽位 / Prompt 措辞（不动分镜语义）
                                   → 只更新 Contract，不回退视觉与分镜
```

**要点**：失效是**级联向下**的（上游变下游全部重确认），但**不动语义的调整只碰执行合同**——把"重新问用户"的成本压到变更的实际影响面上。

### 4.3 cinematic-title-sequence 的 Gate 体系（另一个范本）

四道 Gate：范围确认（15 秒内继续，超出停止本 Skill）→ 三个固定设计问题（主视觉载体四选一 / 屏幕语言 / 准确文字内容）→ 参考图用途 → 影片方案确认。每个问题的**选项文案在 SKILL.md 里逐字固定**（"不得改名、增删一级风格或临时改写选项含义"）。

还有个精妙设计：用户描述了四类主风格之外的风格时——"不把它新增为第五种风格……先按制作机制最接近的一类……在 Gate 2 前用一段普通文本提醒并推荐"——**开放输入被吸附进封闭选项集**，状态空间不膨胀。

## 5. 第四层：能力与执行

### 5.1 design_execute 的输入 schema（mcp-tools-v3 bundle，原文）

```javascript
{
  capabilityId: id(),                    // 如 "video:minimax_v3"（<operation>:<name> 形式）
  prompt: string().max(64000),          // "Describe ONE finished result; use count for variations"
  params: record,                       // capability_get 声明的平铺参数，"Never nest them
                                         //  or pass media paths; references carry media"
  references: [...],                    // 有序输入内容（图/视频/音频），数量与种类由 capability 决定
  count: int 1..N,                      // 变体数；同一 prompt 的多份付费变体
  output: {                             // 必填（媒体）："declare resources and their Composition
    resources: [{mode:"create", name:"视频"}],   // placements"
    composition: {type:{label:"视频"}, name:"作品", placements:[{role:"主视频"}]}
  },
  plugin: { method, contractVersion, target:{compositionId,nodeId,…}, args,
            expectedDraftRevision, baseVersionId }   // 原生编辑器操作走这里
}
```

**output 声明是精髓**：生成之前就要**声明产物如何进入对象模型**（建什么 Resource、放进哪个 Composition、什么角色）——生成结果不是孤儿文件，一落地就有归属。

### 5.2 capability 协议（capability_list/get 的返回结构）

从 `registerModelTools` 源码 + 第二篇模型目录实测：能力以 `<operation>:<name>` 编号（`video:minimax_v3`、`image:nano_banana_2`…），每项带 `description`（"explains what each model or tool can do, **when to choose it** and video output duration ranges"）、`paramSchema`（capability_get 展开）、`knowledgeCard`（指向 `~/.hub/.../knowledge/vendors/*.md` 厂商卡片，第二篇 §9 的 13 张卡在这里被引用）。**模型选择也是协议化的**：agent 先 list 后 get，参数必须"exactly as design_capability_get declares"。

### 5.3 task 状态机（gateway bundle，原文提取）

```
TASK_VIEW_STATUSES = ["accepted", "running", "waiting_user", "unknown", "completed", "failed", "cancelled"]
TASK_PROGRESS_PHASES = ["pending", "queued", "active", "paused", "retrying", "stopped", "done"]
TERMINAL = ["completed", "failed", "cancelled"]
```

两条关键谓词（原文）：

```javascript
awaitsUserCostDecision(task) = task.status==="waiting_user" && task.problem?.source==="billing"
settlesAgentWait(task) = TERMINAL.includes(status) || status==="unknown"
                        || (status==="waiting_user" && !awaitsUserCostDecision(task))
```

**即**：`waiting_user` 有两种——等**用户掏钱**（execute 的等待穿过它继续）和等**用户决策**（agent 的等待在此结束）。task 视图带 `billing.estimatedCredits`、`problem`（含 `upstream` 提供商诊断）、`actions`（可用恢复决策，配合 design_task_resolve 的 `action=retry`）。

### 5.4 代价确认的产品化

execute 工具描述原文："**Cost confirmation belongs to the user in the app; execute waits, and cancelled means declined or unconfirmed.**"——计费确认弹在应用 UI（不在聊天里），agent 的 execute 调用会**阻塞等待**用户在应用里点确认/拒绝。配合 `task.actions` + `design_task_resolve(action=retry)`，拒绝后重试是显式决策而非自动行为。

## 6. 第五层：投递与对象模型

### 6.1 design_deliver（原文 schema 摘录）

```javascript
// 无生成的同步投递：把已有文件/版本/任务产物落进对象模型
{ requestId: "deliver-promo-1",
  sources: [{key:"video", path:"out/promo_cut.mp4"}, {key:"cover", path:"out/promo_cover.png"}],
  output: { resources:[{key:"video",mode:"create",name:"宣传片成片"},
                       {key:"cover",mode:"create",name:"宣传片封面"}], … } }
```

规则（原文）："completed is final; **unknown requires the same requestId and exact input, never regeneration**; blocked requires corrected input with a new requestId, reusing delivered versionIds"——**幂等投递**：未知态用同 requestId 原样重试，绝不再生成。

### 6.2 落地后的世界（第二、四篇已证，此处串成链）

```
outputs[] (task 产物) ──deliver──▶ Resource (身份) ──▶ Version (某次具体内容)
                                        │
                                        └──▶ Composition.members[].{resourceId, role}
                                                （"主视频"、"封面"——成员角色化放置）
                                                     │
                                                     ▼
                                        v3 canvas 节点（第四篇§10：
                                        {type:"version", resourceId, versionId} 引用呈现）
```

**从生成到画布全程带身份**：素材有 stable ref id、生成有 task id、产物有 output key、落地有 resourceId/versionId、呈现有 canvas 节点——这条 id 链是"AI 可持续编辑已生成内容"的基础（改一版 = 新 Version 引用旧血缘）。

## 7. 故事版 UI：人肉分镜入口

画布上的"故事版"（p2 恢复源码，i18n 原文："描述要拆解成分镜的故事…"）给**不走 agent 的用户**一条手动路：

- **输入**：底图（自动成为第一参考，锁定）+ 最多 3 张附加参考（MAX_STORYBOARD_REFERENCES=4）+ 故事文本（≤5000 字）+ 比例 + 网格
- **网格合法性矩阵**（GRID_VALIDITY_MAP，逐项核实）：5 种比例（16:9/4:3/1:1/3:4/9:16）× 1..5×1..5 网格，每比例一张合法集（如 9:16 允许 1,1…5,5 但 2,1 非法——竖屏格子里横排两格装不下）；非法选择自动吸附到**曼哈顿距离最近**的合法网格（nearestValidStoryboardGrid，默认 3×3）
- **提交**：`onSubmit({prompt:"Multi-Shot", params:{horizontal_angle, vertical_angle, zoom}, referenceKeys})`——就是第四篇读到的 Multi-Shot 相机控制面板；网格设置经 `resolveStoryboardGridSelection`（JSON 解析 `grid_setting`，容错回默认）传给后端 vibe_multi_shot 能力，**一次生成整张分镜网格图**

另有相机预设（horizontalAngle/verticalAngle/zoom，clamp 到合法区间）——分镜的**机位**也参数化了。

**定位**：故事版是"用户手动触发一步分镜"的快捷方式；agent 流程（§1-§6）是"全托管"。两者汇合在同一个能力层（vibe_multi_shot / H3）。

## 8. 完整时序：一次"15 秒动漫 PV"端到端走查

以 anime-game-pv 技能为脚本，把五层串成一台戏：

```
T0  用户："用这几张角色立绘做个 15 秒战斗 PV，配热血音乐"
T1  [第1层] 静默 Intake：媒体分析三张立绘 → Candidate Ref Capsule（subject 候选，
    不自动获得 style 权限）；has_valid_image_asset=true
T2  [第1层] 制作路线单选确认卡："使用现有素材制作"（direct_pv）
T3  [第1层] Style Authority Gate 单选："同时参考角色与原画风"（faithful）
    → style_source=立绘素材，无需生成视觉权威图
T4  [第1层] 色彩：faithful 路径按原画风锁定 palette_authority（不强制黑白单色）
T5  [第2层] Render Contract draft→locked：绑定 H3、15s、16:9、参考槽位=三张立绘、
    prompt_budget（5000-7000 字）
T6  [第2层] 写 storyboard_review.md（画布文档节点）：
```

## 9. 失败与回流：为什么"整条重生成"

anime-game-pv 第 6 节原文（默认修复策略）：

> "在 Master Timeline 中定位失败位置 → 修改对应 Panel/Shot/连续性锁 → 新 storyboard_revision → 重新通过分镜门禁 → 重新编译完整 prompt → 重新 Preflight → 新的完整 Render Attempt → 重新检查完整视频，用通过的候选替代旧候选。**不生成局部视频补丁，不把修复后的 Shot 拼接回旧视频，不原样重复失败调用，也不静默切换模型或丢弃参考素材。**"

**工程逻辑**（推断，依据充分）：

1. **拼接是身份灾难**：两条独立生成的片段之间，人物/画风/光照连续性无法保证（模型没有跨调用的记忆），局部补丁几乎必然穿帮
2. **重生成成本可控**：单条 15 秒在模型可靠区内，失败重生成比"生成补丁+拼接+再修拼接缝"的总成本低
3. **状态机保持简单**：候选视频是原子单位，替换即回滚——没有"混合血统"的中间态需要追踪
4. **Prompt 锁定是前提**：正因为"字符级相同的 Prompt"才有"失败重试=原样重放"的语义（deliver 的 unknown 处理同款设计）

这和传统影视"剪辑台救一切"的思路相反：**把可编辑性留给语义层（分镜/合同），把生成层当不可变函数**。

## 10. 设计洞察

**这套流水线真正解决的问题是**：把"生成不可靠、成本不可忽略、质量不可自证"的视频模型，变成**可托管、可审计、可续作**的生产系统。方法清单：

1. **方法论外化为技能文件**——制作流程不是模型权重里的隐知识，是磁盘上可版本化、可审查、可让用户预先读懂的 markdown（18 个技能 = 18 套成文方法论）
2. **状态机显式化 + 门禁强制**——storyboard_status/prompt_status 三态、确认卡唯一授权形式、失效级联传播；LLM 被禁止"善意地"跳步
3. **生成层与语义层分离**——Panel/Shot/Timeline/合同是可编辑的语义层，每次生成是不可变的原子；修复=改语义后重放
4. **参数与叙事隔离**——ref 槽位只放 stable id、叙事写在 prompt 正文、画幅在阶段锁一次（execution_locks）；每类信息只有一个合法的家
5. **成本是人类决策**——计费确认在应用 UI、execute 阻塞等待、拒绝后重试是显式 action
6. **ID 血缘贯穿全程**——ref id → task id → output key → resourceId/versionId → canvas 节点引用，AI 的"持续编辑已有作品"靠这条链成立
7. **把产品边界钉在模型可靠区**——"15 秒一条"不是营销限制，是校验器里 `max_generated_clip_duration_s` 的默认值

**对构建同类系统的直接借鉴**：先写技能（方法论）→ 定义对象模型（Resource/Version/Composition）→ 让 agent 只通过 execute/deliver/task_query 五个受合同保护的动词触达生成 → 每个人类决策点走结构化确认通道。模型换血（H3→H4）时，技能、门禁、对象模型、计费闸门全部不动。
