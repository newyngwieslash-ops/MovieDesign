## 1. 执行摘要

MiniMax Design（内部代号 **hilo**，包名 `@hilo/desktop`）不是一个"画图工具"那么简单——它是一个**集成了本地 AI Agent 运行时的设计工作台**：

- **表层**：Electron + React 19 的设计画布应用（图片/视频/音乐生成、在线编辑器）
- **里层**：捆绑了 **opencode CLI 二进制**、**MCP 工具集**（含 Python 运行时依赖的 Real-ESRGAN 超分模型）、**内置 Chromium 浏览器**（带书签/cookie 导入）、**ComfyUI 后端管理**——一个完整的本地 AI agent 基础设施
- **协议层**：17 个 AI 生成后端（veo3、kling、seedream、nano_banana、minimax_v3…）通过统一的 capability 协议接入
- **代码质量**：Vite/Rollup 打包但**未混淆**，`@hilo/*` 的 26 个 workspace 包边界清晰，源码可读性极高

**对学习者的价值**：这是一个工业级的 Electron + AI Agent 混合架构范本——主进程服务化（VS Code 风格的 InstantiationService/DI）、消息端口直连渲染层、双轨更新、原生桥接，每一层都值得精读。

## 5. 主进程启动链

`out/main/index.js`（全部 393 行已读）的逻辑：

```javascript
// 1) 读 package.json#hiloRelease 验证发布身份（appId/channel）
const release = readPackagedReleaseIdentity();

// 2) Velopack 启动：定位 Update.exe（Windows junction 解析）、
//    setAutoApplyOnStartup(false) —— 不自动应用更新，等应用自己决定
runVelopackEntry({
  loadRuntime, runStartup, markRuntime,      // HILO_UPDATE_BACKEND=velopack
  importMain: () => import("./chunks/index-WiZKxTAT.js").then(n => n.q),  // ← 真 main
  onFatal: showVelopackStartupFailure        // 失败弹窗+写 %TEMP%\minimax-hub-velopack-startup.log
});
```

要点：
- **启动壳与业务 main 分离**：更新运行时起不来时，壳仍能弹错误框引导重装（诊断日志路径写死在 `%TEMP%\minimax-hub-velopack-startup.log`，256 KB 截断）
- 壳里有一整套 **packaged boot/update smoke test** 钩子（`--hilo-packaged-boot-smoke-*` 参数族）——CI 里对打包产物做启动/更新冒烟测试用的，包括 feed URL 白名单校验（必须是生产 origin + `velopack/<channel>/builds/<version>/<stamp>` 不可变路径格式 + SHA-256 资产校验）。**这是防止更新链被投毒的安全设计**，值得借鉴
- Windows 上还处理了**旧版卸载入口可见性恢复**（reg.exe 删 `SystemComponent` 注册表值）

真正的 main（`index-WiZKxTAT.js`，9.9 MB）里可见 VS Code 同款的 **InstantiationService 依赖注入容器**（`IInstantiationService`、`createDecorator`、`DisposableStore`、`Emitter`——从导出符号清单确认）与 `ScopedStorage` 工作区存储。

## 6. IPC 协议全景

| 域 | 通道示例 | 数量级 |
| --- | --- | --- |
| `@hilo/base` 握手协议 | `hilo:hello` / `hilo:message` / `hilo:disconnect`（消息总线握手） | 3 |
| 窗口管理 | `window:minimize/maximize/close/is-fullscreen…` | ~8 |
| 应用/Shell | `app:get-version`、`shell:open-external`、`shell:inspect-file-reference` | ~20 |
| 剪贴板 | `clipboard:read/write-text/write-image/write-file` | 5 |
| **文件系统** | `fs:exists/read-dir/read-text-file/write-*/mkdir/rename/delete/stat/copy/watch` | ~14 |
| 对话框 | `dialog:open/save` | 2 |
| **热更新** | `hot-update:check/clear-cache/reload/get-version(-sync)` | 5 |
| **Velopack 更新器** | `updater:check/download/cancel-download/dismiss/get-status…` | ~6 |
| **认证** | `auth:login/logout/renew-token/fetch-user-info` + token 变更广播 | ~10 |
| **存储** | `storage:get/set-tokens/user/desktop-config/workspace-*/global-*` | ~14 |
| 通知/日志 | `notification:*`、`log:write/export/upload` | ~6 |
| **内置浏览器** | `browser:*`（标签页/导航/下载面板/设备预览/标注/截图/导入书签 cookie…） | ~50（最大域） |
| 浏览器插件 | `BROWSER_PLUGIN_CHANNELS.{GET_CONFIG/EVENT/COMMAND/RENDERER_EVENT}` | 4 |
| opencode | `opencode:restart` | 1 |
| 网络/性能/内存 | `network:*`、`perf:capture-{cpu,heap,trace,netlog}`、`memory:*` | ~10 |
| 菜单/深链/截图 | `menu:*`、`deeplink:received`、`screenshot:start` | ~5 |

**设计观察**：
1. 通道名采用 `domain:action` 命名空间约定，字符串字面量而非 Symbol（preload 里有 `ALLOWED_IPC_CHANNELS` 白名单 Set 校验——渲染进程不能发明通道，只能用枚举里的）
2. `fs:*` 通道本质是把一套**受限文件系统 API** 暴露给渲染层——`isInsideOptionalPath`、`rewriteUnderRoot`、`toExtendedLengthPath` 等符号说明主进程对路径做了根目录围栏与越权检查（这是 Electron 应用防 renderer 逃逸的关键模式）
3. 认证令牌有完整的**双向广播**（`auth:changed-to-main/renderer`、`auth:expired-*`）——多窗口令牌同步

## 8. 内置浏览器子系统

从 IPC 通道 + `browser-tab.cjs` preload（59 KB）还原的架构：

- 每个浏览器标签页是一个**独立 BrowserView/WebContents**，独立 `session` + `partition`（BrowserWindow 配置里观察到 `partition: dynamic`）
- 下载有完整面板状态机（`browser:downloads-{open,close,update}-panel`、`download-transfer`、`download-save-prompt`）
- **书签/Profile 导入**：`browserProfileImport.{listProfiles,importCookies,importBookmarks,onProgress,onRequested}` ——能列出并导入系统浏览器的 profile（从"requested→进度→完成"的三段式通道看，导入走主进程特权代码，渲染层只发指令）
- **插件系统**：`bundled-plugins/` + `BROWSER_PLUGIN_CHANNELS` 四通道（get-config/event/command/renderer-event）——浏览器页面里可注入插件
- `setNativeViewOcclusion`——原生视图遮挡管理，说明浏览器视图是原生级叠加在渲染页面上（不是 iframe）

## 9. AI 模型后端协议

`v3-workbench.cjs` preload 开头直接铺开了 **17 个后端常量**（`BACKEND_*`）——这是 v3 工作台的模型能力协议层：

```
图像：nano_banana(即Gemini图像) · midjourney · seedream · minimax_v3
视频：veo3 · kling · kling_avatar · wan_i2v · vibe_multi_shot · vibe_storyboard · vibe_relight · seedance
音乐：minimax_music · elevenlabs_music · seedaudio
语音：minimax_tts
其他：openai
```

协议实现细节（源码可读）：
- `capabilities/request.js` 定义 `wire()` 参数序列化 + `intInRange` 范围校验 + `reject()` 抛 `CapabilityInputError`——**统一的能力参数协议**，每个后端声明自己的参数 schema（如 `IMAGE_ASPECT_RATIO`/`IMAGE_RESOLUTION` 枚举、`durationParam` 秒数区间"向上取整、封顶、继承参考时长则拒绝"）
- 传输：`__HILO_V3_PORT_HOST__.connect()` 通过 **MessageChannel 端口直连**（preload 中 `receivePort` 只接受恰好 1 个 port 的握手事件，重复投递直接 `port.close()`——防重放），绕过 ipcRenderer 序列化开销，适合画布这种高频交互
- `__HILO_V3_NATIVE_HOST__` 提供 `ELECTRON_CAPABILITIES` 能力集（fs 等）给 v3 页面
- v3 资产带 `bundle-manifest.json`（每个文件 SHA-256）——**渲染层热更新的完整性校验**

## 10. Agent 子系统

这是这个应用最有学习价值的部分。从 headless-entry.js + 资源目录 + 环境变量三面印证：

## 11. 上传功能追踪实录

用 REA `trace-application-feature` 以字符串种子 `/api/upload` 双向追踪（终端路径 1,435 条，观察事实 7,170 / 推断 6,998 / 未知 0），再对照 bundle 源码，还原的完整链路：

```
渲染进程 (CanvasArea/EditorInterface)
  │  EditorInterface 里的 Clip Studio 导出宿主 createNativeClipStudioHost()
  │  upload(blob, name, staging):
  │      form = new FormData()
  │      form.append("file", blob, name)          ← 文件本体
  │      if (staging) form.append("staging","true") ← 暂存模式
  │      POST /api/upload  → gateway.fetch()       ← __HILO_V3_NATIVE_HOST__ 提供的编辑器网关
  ▼
本地 Gateway (127.0.0.1:8001)
  │  返回 { ok, relative|path, id? }
  │  失败路径: HTTP 状态 → "Editor upload failed: HTTP {status}"
  ▼
渲染进程拿到 { __hubBlobRef: true, path, assetId? }
  │  blob 引用（不上传者本地路径）作为 source 传给编辑器方法
  ▼
编辑器操作 insert(method, { source: blobRef, ... })
```

**关键设计**（源码逐行核实）：
1. **上传走本地 gateway 而不是直连云端**——`nativeEditorGateway.fetch()`，即文件先落到本地资产中心（`resolveAssetCenterRoot`），云端任务引用 `__hubBlobRef` 引用而非字节
2. `staging=true` 区分暂存上传（草稿）与正式上传
3. 响应里的 `relative ?? path` 双字段兼容——版本演进的痕迹
4. 主进程另有 17 处 `uploadFile`、112 处 `multipart` 相关代码（DAG 任务、日志上传 `log:upload`、诊断上传 `diagnostics.uploadLogs` 都有各自的上传通道）

**REA 追踪的诚实边界**：种子只命中 1 个 endpoint 节点（`customMcpVault` 的 `globalStorage.get` 机制候选），静态图把全应用可达子图都返回了（5,621 节点）但**不执行代码**；真实调用流是靠读 bundle 源码补全的——这正是 REA 的设计意图：Evidence 给你地图，代码细节自己精读。

## 13. Electron 安全姿态

`rea inspect-electron-fuses` 实测 9 个 fuse（偏移 193,899,536，wire v1）：

| Fuse | 状态 | 含义 |
| --- | --- | --- |
| RunAsNode | **enabled** | `--run-as-node` 可用（打包场景需要；对攻击者也意味着可用 node 模式起进程——Velopack 壳依赖它做 smoke test） |
| EnableCookieEncryption | disabled | Cookies 未启用 OS 级加密 |
| EnableNodeOptionsEnvironmentVariable | **disabled** | `NODE_OPTIONS` 注入被禁 ✓ |
| EnableNodeCliInspectArguments | **disabled** | `--inspect` 调试参数被禁 → **这就是运行时 CDP 观察做不了的原因**（需带 `--remote-debugging-port` 重启才能开） |
| EnableEmbeddedAsarIntegrityValidation | **disabled** | **asar 完整性校验未启用** —— 任何人可改 app.asar（对逆向者是好事，对安全是缺口） |
| OnlyLoadAppFromAsar | **enabled** | 只从 asar 加载应用 ✓ |
| LoadBrowserProcessSpecificV8Snapshot | disabled | — |
| GrantFileProtocolExtraPrivileges | enabled | file:// 协议有额外权限 |
| WasmTrapHandlers | enabled | — |

**结合窗口配置**（`contextIsolation: true`、`nodeIntegration: false`、动态 `partition`）综合评价：**进程隔离是标准姿势，但 asar 完整性校验缺失**——应用没有做防篡改自校验（Electron 官方 fuse 本可开）。学习注意：若目标是"分析"，这是入口；若目标是"加固"，这是反面教材。
